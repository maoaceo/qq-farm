# SQLite 用户存储与严格账号隔离

## 行为变化

所有面板身份（包括超级管理员）在游戏账号列表、设置中的账号管理、运行日志、账号日志、HTTP 操作和 Socket.IO 订阅中，只能访问归属自己的游戏账号。

管理员不再有查看全部游戏账号的例外，删除「账号归属分配」页面及转移 API。管理员仍可创建/禁用面板用户、重置用户密码、设置 Turnstile 和实例运行参数；这些是平台管理权限，不是查看游戏账号的接口。

旧账号没有 ownerId 时仍默认归 admin，防止升级时随意改变原有归属；已有 ownerId 不变。若历史部署中归属字段本来就不正确，本次不会根据 QQ/备注猜测真正归属，需要停服核实原始数据及备份。游戏账号和自动化配置当前仍由上游 JSON 存储实现，本次迁移的是普通面板用户及第三方身份关系。

## 用户数据库

普通用户名、加盐密码哈希、禁用状态、创建时间和 OIDC 绑定改为 SQLite：

- 源码：`core/data/users.sqlite`
- Docker：`/app/core/data/users.sqlite`，位于现有持久化数据卷
- 超级管理员信息当前仍沿用 `admin.json`，未迁移或重置。
- 会话仍在内存，服务重启需重新登录。

使用事务、唯一用户名约束（大小写不敏感）、唯一 `(issuer, subject)` 身份约束、外键、WAL 和锁等待。SQL 参数均使用绑定参数；不是把整个 JSON 内容直接放进单个数据库字段。

## 自动迁移

首次打开数据库时执行一次迁移：

1. 如果存在旧 `users.json`，严格校验并复制为 `users.json.pre-sqlite.bak`（已有备份不覆盖）。
2. 在事务中导入所有用户及身份关系，保留原 ID 和密码哈希；游戏账号 ownerId 因此不变。
3. 成功后写入迁移标记，后续以数据库为准，不会把过时 JSON 再导入覆盖新密码。
4. 原 JSON 不删除、不更新，留作备份。遇到损坏、重复用户名或身份冲突会中止迁移并报错，不会静默创建空用户库继续运行。

升级前必须停服并完整备份数据卷。SQLite 迁移完成后不能随便回滚旧代码，旧 JSON 不会包含后来注册、禁用和改密的数据。

## 部署及原生依赖

```bash
git pull --ff-only
docker compose up -d --build
```

Dockerfile 已为 SQLite 原生依赖的编译回退增加 python3/make/g++，pnpm 已允许 better-sqlite3 安装脚本。现有数据卷保持不变，不要执行 `docker compose down -v`。

源码部署执行 `pnpm install --frozen-lockfile && pnpm build`。没有预编译包时需安装平台编译工具，依赖必须在实际运行平台和 Node 版本下安装，不能直接拷贝其他架构 node_modules。使用原来的 Node18 pkg 单文件构建流程不保证自动包含 SQLite 原生动态库，推荐源码或 Docker 部署。

## 备份

最简单可靠的方法：停服后复制完整数据目录，包含 `users.sqlite` 和存在的 `users.sqlite-wal` / `users.sqlite-shm`，再启动。不能在运行中只复制 SQLite 主文件就认为备份完整。备份包含哈希和账号凭据，需限制权限。

数据库不提供加密或防止服务器所有者访问文件的能力。这里保证的是应用接口的归属权限；持有宿主机/数据库权限的人仍可读写数据，平台管理员的用户密码重置权限也需要信任与审计。
